# 223P reference for point mapping

Checked against 223P `v1.0.0-2026`. Namespace `s223:` is `http://data.ashrae.org/standard223#`.
Verify names against the version you have loaded (queries 1, 3 and 4 in `queries.md`).

## 1. Choosing the property class

A point becomes a `Property` of the entity it characterizes. Four concrete classes cover
almost everything:

| | Quantifiable (numeric, has a unit) | Enumerated (one of a fixed set) |
|---|---|---|
| **Observable** (measured or reported) | `QuantifiableObservableProperty` | `EnumeratedObservableProperty` |
| **Actuatable** (written by control or an operator) | `QuantifiableActuatableProperty` | `EnumeratedActuatableProperty` |

Rules of thumb:
- **Observable:** sensor readings, feedback, calculated values, and statuses the controller
  reports (AI, most read-only AV/BV/MV).
- **Actuatable:** outputs to equipment, setpoints, limits, delays and other parameters an
  operator sets, enables and inhibits, and mode selections (AO, commandable AV/BV/MV).
  "Commandable" in BACnet is a hint, not the rule: a commandable BV that the controller only
  reports is still observable.
- **Quantifiable vs enumerated** follows the value, not the BACnet type. An analog value
  holding a mode number is enumerated, and a binary position feedback is still enumerated.

**Owner.** Attach the property to the entity it describes:
- a temperature *of the air leaving a VAV* belongs to the VAV's outlet `ConnectionPoint`;
- a damper position belongs to the `Damper`;
- a zone temperature or an occupancy belongs to the `Zone` (or its `DomainSpace`);
- controller housekeeping belongs to the `Controller`.

Picking the connection point rather than the equipment matters for anything with a medium.

## 2. Quantifiable properties

Every quantifiable property needs `qudt:hasQuantityKind` and `qudt:hasUnit`, and they must be
compatible; validation checks this when the QUDT vocabularies are loaded. These pairs were used
and validated in a real VAV model:

| BMS unit | Quantity kind (`quantitykind:`) | Unit (`unit:`) |
|---|---|---|
| °F | `Temperature` | `DEG_F` |
| CFM | `VolumeFlowRate` | `FT3-PER-MIN` |
| % | `DimensionlessRatio` | `PERCENT` |
| ppm | `DimensionlessRatio` | `PPM` |
| inWC | `Pressure` | `IN_H2O` |
| min / s / h | `Time` | `MIN` / `SEC` / `HR` |
| in | `Length` | `IN` |
| BTU/h | `HeatFlowRate` | `BTU_IT-PER-HR` |
| (count) | `Count` | `NUM` |
| (none) | `Dimensionless` | `UNITLESS` |

Also:
- **Differences and offsets** (a setpoint offset, a delta-T, a differential pressure): add
  `qudt:isDeltaQuantity true` and `s223:hasAspect s223:Aspect-Delta`.
- **What is measured.** Use `s223:ofMedium` for the fluid, for example `s223:Fluid-Air` or
  `s223:Water-HotWater` (`s223:Water-ChilledWater`, `s223:Water-Steam`). For a concentration,
  use `s223:ofConstituent` instead, for example `s223:Constituent-CO2`. Fluids sit under
  `s223:Mix-Fluid`, and constituents under `s223:Medium-Constituent`.

## 3. Enumerated properties and enumeration kinds

An enumerated property names its value set with `s223:hasEnumerationKind`. Its value, when
recorded, is one member of that kind.

**How 223P encodes kinds and members.** Every kind and every member is an `s223:Class`, an
`sh:NodeShape`, *and an instance of itself*. Members are subclasses of their kind:

```turtle
s223:Binary-OnOff a s223:Class, sh:NodeShape, s223:Binary-OnOff ;
    rdfs:subClassOf s223:EnumerationKind-Binary .
s223:OnOff-On a s223:Class, sh:NodeShape, s223:OnOff-On ;
    rdfs:subClassOf s223:Binary-OnOff .
```

So "is it a class?" can't tell a kind from a member. Having no subclasses can: a member is a
leaf. Some kinds, such as the aspects and roles, are one level deep. Others nest: under
`EnumerationKind-Binary` sit the kinds `Binary-OnOff`, `Binary-Logical` and `Binary-Position`,
and under those, their members.

**The value-set kinds useful for points (v1.0):**

| Kind | Members |
|---|---|
| `Binary-OnOff` | `OnOff-On`, `OnOff-Off` |
| `Binary-Logical` | `Logical-True`, `Logical-False` |
| `Binary-Position` | `Position-Open`, `Position-Closed` |
| `Occupancy-Motion` | `Motion-True`, `Motion-False` |
| `Occupancy-Occupied` | `Occupied-True`, `Occupied-False` (generic occupancy) |
| `Occupancy-Presence` | `Presence-True`, `Presence-False` |
| `DayOfWeek-Weekday` / `-Weekend` | `Weekday-Monday` ... `Weekend-Sunday` |
| `Numerical-Frequency`, `-Voltage`, `-NumberOfElectricalPhases` | e.g. `Frequency-60Hz` |

That's the complete list of 223P value sets relevant to points. There are no operating modes,
zone states, run states, enable states, alarm states or unit selections. Multi-state points
nearly always need an extension kind (section 8).

**Shapes that require a specific kind.** `s223:OccupantMotionSensor` must observe a property
with kind `s223:Occupancy-Motion`, and extensions add more (section 9). Run query 5 on a kind
before relying on it, and on a sensor class before using it.

## 4. Aspects, roles and domains as qualifiers

These are also enumeration kinds, but they qualify a property or entity rather than being its
value set:

- **Aspects** (`s223:hasAspect` on a property) say *which* value of the quantity this is:
  `Aspect-Setpoint`, `-Maximum`, `-Minimum`, `-Delta`, `-Deadband`, `-Threshold`, `-HighLimit`,
  `-LowLimit`, `-Nominal`, `-Rated`, `-Alarm`, `-Fault`, `-OperatingMode`, `-OperatingStatus`,
  and nameplate aspects (`-Manufacturer`, `-Model`, `-SerialNumber`, `-CatalogNumber`).
- **Roles** (`s223:hasRole` on equipment or connection points): `Role-Supply`, `-Return`,
  `-Discharge`, `-Exhaust`, `-Relief`, `-OutdoorAirIntake`, `-Recirculating`, `-Heating`,
  `-Cooling`, `-Ventilating`, `-Dehumidifying`, `-Economizer`, `-HeatRecovery`, `-Primary`,
  `-Secondary`, and others.
- **Domains** (`s223:hasDomain` on zones and spaces): `Domain-HVAC`, `-Lighting`, `-Occupancy`,
  and others.

`hasAspect` accepts any enumeration kind, so a property can also carry a role
(`Role-Cooling` on a cooling setpoint) or a custom mode from an extension as an aspect. That's
how to express "cooling occupied maximum airflow setpoint" in 223P: a quantifiable actuatable
property with aspects `Setpoint`, `Maximum`, `Role-Cooling` and an occupied-mode aspect. Stack
aspects rather than inventing a compound term.

## 5. State-text synonyms

Controllers label binary states many ways. Map by meaning, keep the raw text in the state
mapping (section 7), and only extend when the meaning genuinely differs:

| State texts (inactive / active) | 223P kind | Notes |
|---|---|---|
| Off / On | `Binary-OnOff` | |
| Stopped / Running | `Binary-OnOff` | run status |
| Idle / Override, Off / Active, Off / Initiated, Off / Calibrating | `Binary-OnOff` | an activity is running or not. Put what the activity is in an aspect. |
| False / True, No / Yes | `Binary-Logical` | |
| Disabled / Enabled, Not Permitted / Permitted | `Binary-Logical` | enables and inhibits |
| Open(ed) / Closed | `Binary-Position` | inactive is often Open for contacts: check the order |
| No Motion / Motion | `Occupancy-Motion` | required by `OccupantMotionSensor` |
| Vacant / Occupied, Unoccupied / Occupied | `Occupancy-Occupied` | |
| Auto / Manual, Warm Air / Cool Air, and other two-state choices | *extension* `Binary-X` | no 223P equivalent |

Read the order from the data (inactive = 0, active = 1). Don't assume the "on" meaning is the
active state. The window contact in the VAV example has inactive = Opened.

## 6. Relations

- **Between properties:**
  - `s223:hasSetpoint` (measured → setpoint);
  - `s223:hasThreshold` (measured → alarm or limit threshold);
  - `s223:hasDeadband`;
  - `s223:hasAlarmStatus` (measured → alarm status property).
- **Sensors:** a `Sensor` subclass (`TemperatureSensor`, `PressureSensor`,
  `ConcentrationSensor`, `OccupantMotionSensor`, ...) with `s223:observes <property>` and
  `s223:hasObservationLocation <connection point or space>`.
- **Actuators:** `s223:actuatedByProperty <property>` on the `Actuator` (or the equipment), and
  `s223:actuates <equipment>`.
- **Control logic:** a `s223:Function` with `s223:hasInput` and `s223:hasOutput`, executed by the
  controller (`s223:executes`).

Validation warns when an actuatable property has no `actuatedByProperty`, or an observable one
has no sensor. On a controller point list, where most points are software values, expect many
such warnings. They're advisory, and a baseline diff keeps them from hiding real problems.

## 7. BACnet external references and state mappings

```turtle
bldg:p-BV63 s223:hasExternalReference bldg:bacnet-BV63 .
bldg:bacnet-BV63 a s223:BACnetExternalReference ;
    bacnet:device-identifier "device,10214" ;
    bacnet:object-identifier "binary-value,63" ;
    bacnet:object-name "Window Contact" .
```

Here `bacnet:` is `http://data.ashrae.org/bacnet/2020#`. Add `bacnet:property-identifier`
(for example `"log-buffer"` for a trend log) when the reference isn't the present value.

A property can't have both an internal and an external reference. When a software value mirrors
a physical I/O point (AV50 mirroring AI2), make them two properties joined by a `Function`
rather than one property with two references.

223P has no term for which BACnet state value corresponds to which member. If that matters (it
does whenever someone will read or write the point through the model), add a small extension.
This pattern has been used and validated:

```turtle
bldg:bacnet-BV63 dibt:hasBACnetState bldg:bacnet-BV63-state-0 .
bldg:bacnet-BV63-state-0 a dibt:BACnetState ;
    dibt:stateValue 0 ;                       # binary: 0 inactive, 1 active; multi-state: 1..n
    dibt:stateText "Opened" ;                 # raw text, typos included
    dibt:hasEnumerationValue s223:Position-Open .
```

Check that every mapped member is a subclass of the property's kind. A script can do this in a
few lines.

## 8. Writing an extension

Mirror 223P's own encoding so tools and shapes treat the new terms like standard ones:

```turtle
ext:Binary-AutoManual a s223:Class, sh:NodeShape, ext:Binary-AutoManual ;
    rdfs:subClassOf s223:EnumerationKind-Binary ;
    rdfs:label "Auto/manual" ;
    rdfs:comment "Whether a value is calculated automatically or set manually" .
ext:AutoManual-Auto a s223:Class, sh:NodeShape, ext:AutoManual-Auto ;
    rdfs:subClassOf ext:Binary-AutoManual ;
    rdfs:label "Auto" ; rdfs:comment "Calculated automatically" .
```

- **Parents:** a two-state kind goes under `s223:EnumerationKind-Binary`, a multi-state kind
  under `s223:EnumerationKind`, and a new aspect under `s223:EnumerationKind-Aspect`.
- **Naming:** follow 223P's patterns: `Binary-X` or `EnumerationKind-X` for kinds, `X-Member`
  for members, `Aspect-X` for aspects.
- **Members:** list every state the device supports, not just the ones in the current export.
  Every state is a value the point can take. If you only have some, mark the kind as partial in
  its comment until you get the full state-text array.
- **Operating modes:** Guideline 36 operating modes (Occupied, Occupied-standby, Warm-up,
  Cool-down, Setup, Setback, Freeze protection setback, Unoccupied) aren't in 223P. One kind
  holding them can serve both as the value set of a mode point and as an aspect on
  mode-specific setpoints.
- **Separate file:** keep extensions in their own namespace and file, and load that file
  wherever the model is loaded.

## 9. Extension shapes that constrain choices

The ASHRAE G36 extension (`g36:`) adds shapes that can *infer* G36 classes (`g36:Zone`,
`g36:VAVTerminalWithReheat`, `g36:Damper`, ...) when a model has the right structure. Some of
them require particular kinds:

- `g36:Zone` expects a window-switch property with `s223:Binary-OnOff`, observed at a
  `s223:Window`, and a binary occupancy property (any `s223:EnumerationKind-Occupancy`).
- `g36:Fan` expects a start/stop command with `s223:Binary-OnOff`.
- `g36:TwoPositionDamper` expects a command with `Aspect` `Binary-Position` and a binary kind.

These checks are Info severity, so ignoring them doesn't break validation. But the G36 class
won't be inferred, and a downstream tool looking for `g36:Zone` won't find the zone. When exact
semantics (Opened/Closed → `Binary-Position`) and a shape (`Binary-OnOff`) disagree, choose
deliberately and report it. Query 5 finds these requirements for any term.
